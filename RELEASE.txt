WHO GOES FIRST? — 1.0.0 RELEASE CANDIDATE

RUN LOCALLY
Requires Node.js 22 or newer. No application runtime dependencies or npm install
are needed. In this project directory:
  npm start
Open http://127.0.0.1:4173 . This builds and serves only dist/, not repository files.
Stop with Ctrl+C. HOST and PORT can be specified explicitly if needed.

BUILD / DEPLOY
  npm run build
Publish only the contents of dist/ to a static HTTPS host. There is no backend,
account service, database, analytics, external font, or runtime CDN dependency.
Prefer an atomic deploy (upload a complete release, then switch it live) and keep
the previous release for rollback. Do not upload files in-place during live use.
Use a canonical trailing slash for a subdirectory, e.g. /games/first/ .
Relative URLs, manifest scope, installation metadata, and offline resources work
at the origin root or a nested directory. Do not serve the source sw.js as the
production worker: the build supplies a content-derived cache version.

GITHUB PAGES
Repository: https://github.com/bkrabach/who-goes-first
Website: https://bkrabach.github.io/who-goes-first/
The pinned .github/workflows/pages.yml workflow tests and builds on every push
to main, then publishes only dist/ using the official Pages artifact deployment.
Enable Pages with GitHub Actions as its source before the first deployment.
No repository content outside dist/ is deployed as part of the website.
The expected project URL uses the repository name as a subdirectory.
GitHub Pages supplies its own cache/security response headers and ignores
_headers. The HTML carries an additional content-security policy for this host.

The supplied _headers file is understood by compatible static hosts such as
Netlify and Cloudflare Pages. For other hosts apply equivalent headers yourself:
correct MIME types; no-cache/revalidation for HTML, JS, CSS, and service worker;
X-Content-Type-Options: nosniff; the supplied compatible CSP and referrer policy.
Do not use a long immutable cache lifetime for these stable filenames.

build-info.json records input and output SHA-256 values. Builds use an explicit
allowlist, verify staged bytes, and retain previous generated dist directories
as .dist-previous-* (ignored by Git). They do not erase unrelated source work.

OFFLINE / UPDATES
The first online visit caches the game, themed surfaces, icons, and audio.
An updated worker waits by default; it never automatically interrupts a spin.
A small dot on Settings marks a ready update. Use Settings > Apply update when
idle. Close other app tabs/installed windows first if prompted. The app reloads
with the new release without clearing players or preferences.
Older releases without this control need a one-time close of EVERY tab and
installed window for this site, then reopen. Refresh alone may retain the old
offline release. Do not clear browser data to update: that erases saved players.
Private browsing or site-data cleanup can remove the cache and saved data.

TESTS
  npm test
Browser suites use an installed Playwright (or playwright-core) and Chromium:
  PLAYWRIGHT_MODULE=/absolute/path/to/playwright-or-playwright-core/index.mjs npm run test:e2e
Alternatively install the development toolchain in your own environment and
omit PLAYWRIGHT_MODULE when the 'playwright' package resolves normally.
The repo does not auto-install browser packages or system dependencies.
The build requires no browser tool; original image/audio assets are checked in.

Tests cover picker/editor behavior, settings persistence, backup confirmation and
validation, stale-Undo prevention, production CSP, mobile/tablet/desktop and
landscape layouts, keyboard focus, offline reload, nested deployment paths,
PWA installability metadata, worker upgrades, original-artwork rendering,
progressive motion blur, coast-and-settle movement, cue timing, mixed audio
headroom, and opaque-origin/no-network preview behavior.
Optional source provenance checks accept YAY_SOURCE and WHEEL_SOURCE pointing to
the original user-provided recordings. Those recordings are not bundled in full.

DATA / ACCESSIBILITY
Sample players are ephemeral browser-only demonstrations, not a saved roster.
Players always edits the user's actual crew and focuses name entry when empty.
Installed-app windows do not use the demonstration crew. Existing custom lists,
all-inactive lists, deliberate saved-empty lists, and imported lists are preserved.
Only the exact unmarked original nine-name/default-toggle roster is recognized
as old demo data. A historic explicit save identical to those defaults cannot
be distinguished; no storage is changed automatically by this recognition.
Unreadable roster storage is retained; creating a replacement requires explicit
confirmation, and no empty recovery backup is exported.
Players and settings are local only. Export players from Settings before changing
devices or clearing site data. Import replaces the current list only after explicit
confirmation. No account is needed and there is no cross-device synchronization.
Sound effects can be disabled, volume adjusted, and reduced motion selected.
The operating system's reduced-motion preference is always respected.
The optional browser installation tip is dismissed using a separate local
preference. Installed app windows and embedded previews do not show it. Settings
always retains consumer-oriented installation steps. The desktop Fit portrait
window button is a user-triggered best-effort resize, not an aspect-ratio lock;
browser/OS window rules can refuse it. No automatic resizing is performed.
New square, opaque icons use fresh filenames and a separate maskable safe-zone
variant. Existing Dock/home-screen icons may update on the browser's schedule.
The macOS "Data Access Blocked" notification is an OS/browser integration issue
whose denied resource has not been identified. The website requests no broad
filesystem access; imports use an explicitly selected file and exports a
user-triggered download. Do not grant Full Disk Access or clear site data as a
workaround. Source reference: https://web.dev/learn/pwa/windows/
Approved default: 3.2-second coast/assisted settle with progressive directional
blur, natural-speed wheel collage during spinning, and one Yay at the actual stop.
Drag the parchment reel with a finger or primary mouse button, then release to
spin in that direction. Names follow the drag and wrap without blank gaps; taps,
horizontal gestures, canceled pointers, and returning to the starting point do
not draw a winner. The normal spin button and keyboard path remain available.
Gesture direction never changes any player's chance of being picked.
The portrait gold face is a bounded artifact on an illustrated wooden workbench
when there is at least 48px of extra horizontal space. Otherwise it remains
edge-to-edge with no device trim. A non-repeating transparent layer adds large
stains, scratches and worn patches below the unchanged reel and controls.
The wood and patina are bundled in both offline releases and the Canvas preview.
Supporting installed desktop browsers may blend artwork behind native window
controls using Window Controls Overlay. A transparent, reserved strip remains
draggable; content and dialogs stay below it. This is not desktop transparency.
Unsupported browsers retain their normal title bar. Native OS dragging and window
controls require device testing; geometry tests do not establish that integration.

RELEASE BOUNDARIES
Publication is configured for the repository and website above. Consult the
repository's Pages workflow and direct site checks for the current deployment
state; a successful local build does not by itself establish publication.
The HTML Canvas preview is sandboxed, may lack persistent storage, and deliberately
disables service-worker registration; it is not an installation/offline proof.
Chromium was exercised. Actual Safari/iOS and Android home-screen installation,
physical audio output, and device performance still require final device checks.
WebKit and Firefox test binaries were not present in the installed environment.
